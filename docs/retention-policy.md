# GovChat-NL data-retention policy

This policy is enforced by GovChat-owned code and deployment configuration in this repository. The upstream LibreChat checkout is read-only. A dedicated `govchat-retention` container runs the worker from the same pinned LibreChat image as the web service, without starting an HTTP server. It initializes LibreChat's own database models, app configuration, and file-storage services, then performs idempotent application-level cleanup using a MongoDB lease. It does not issue raw collection deletes for application data. The default interval is 60 minutes.

## Retention controls

| Data | Default | Configuration | Age basis and deletion |
| --- | ---: | --- | --- |
| Conversations and messages | 720 hours (30 days) | `GOVCHAT_CHAT_RETENTION_HOURS` | Latest message creation time; a conversation with no messages uses its creation time. The GovChat sweep invokes LibreChat's conversation cascade so message records, descendants, access grants, and related stored files are removed. The cutoff includes one sweep interval of safety margin. |
| User-uploaded files | 30 days | `GOVCHAT_UPLOAD_RETENTION_DAYS` | File record creation time. Expired records go through LibreChat's storage-deletion sweep before Mongo metadata is removed, so local and configured storage backends use their native deletion strategies. The cutoff includes one sweep interval of safety margin. |
| Native prompt-library groups and revisions | 730 days | `GOVCHAT_PROMPT_RETENTION_DAYS` | Conservative age fallback from group `updatedAt`, or `createdAt` if no update timestamp exists. This is **not represented as exact last-use tracking**. Langfuse-managed groups are excluded because their source is external. Deleting a group also deletes its revisions and LibreChat permissions. |
| Generated GovChat images | 30 days | `GOVCHAT_GENERATED_IMAGE_RETENTION_DAYS` | File modification time; only filenames generated by the GovChat image flow are removed from the shared images directory. |
| Async image-job state | 24 hours | `IMAGE_JOBS_TTL_HOURS` | Existing admin job cleanup removes terminal job records after this TTL. This is separate from generated image-file retention. |
| n8n executions | 718 hours (29 days 22 hours) + native prune sweeps | `N8N_EXECUTION_RETENTION_HOURS`, `N8N_EXECUTION_HARD_DELETE_BUFFER_HOURS`, `N8N_EXECUTION_HARD_DELETE_INTERVAL_MINUTES`, `N8N_EXECUTION_SOFT_DELETE_INTERVAL_MINUTES` | PostgreSQL execution records: save errors only, do not save successful or manual executions, and enable n8n's soft/hard pruning. The two-hour margin covers the default 60-minute soft-delete and 15-minute hard-delete polling intervals. |
| n8n runtime logs | 30 days | `N8N_LOG_RETENTION_DAYS` | n8n writes error-level logs to the shared log volume. The dedicated log-pruner rotates hourly and removes rotated log files older than this setting. |

The cleanup interval is controlled by `GOVCHAT_RETENTION_SWEEP_INTERVAL_MINUTES` and is capped at half the shortest retention window. Cutoffs are advanced by one sweep interval so a healthy, running deployment processes records before their maximum age. If the worker is unavailable, it restarts independently of the web service; data cleanup resumes after it reconnects. This cannot guarantee deletion by the wall-clock deadline during an outage, an unavailable storage backend, a failed worker startup, or repeated deletion errors; such failures are logged and retried. The policy is therefore not an unconditional erasure guarantee until monitored on the actual deployment and its storage/backup layers.

## n8n policy

The Compose service sets:

- `EXECUTIONS_DATA_SAVE_ON_ERROR=all`
- `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`
- `EXECUTIONS_DATA_SAVE_MANUAL_EXECUTIONS=false`
- `EXECUTIONS_DATA_PRUNE=true`
- `EXECUTIONS_DATA_MAX_AGE` from `N8N_EXECUTION_RETENTION_HOURS` (default 718 hours)
- `EXECUTIONS_DATA_HARD_DELETE_BUFFER=0`, so no extra post-retention grace period is added
- hard-delete pruning every 15 minutes and soft-delete pruning every 60 minutes by default
- `N8N_LOG_LEVEL=error`

Therefore successful workflow payloads are not retained as execution records; failed execution records are soft-pruned at 718 hours and physically hard-deleted by n8n's configured sweeps. With the 0-hour buffer and default intervals, the expected hard-delete completion is before 30 days. n8n's own application log file is error-only and rotated/pruned by the GovChat log-pruner after the configured age. Container stdout/stderr may still contain brief entrypoint/engine lifecycle output and is separately capped by Docker's local size/file-count rotation.

## Data-removal notes and boundaries

- Uploaded files are removed through LibreChat's file service, not by deleting Mongo metadata alone. Failed backend deletion remains queued for the built-in retry sweep; operators must monitor `[govchat-retention]` and LibreChat file-sweep errors.
- Prompt expiry is intentionally an age fallback, not a precise last-use deadline. If the organization later requires exact prompt last use, add an explicit use timestamp in a version-pinned GovChat overlay and migrate old prompt groups conservatively.
- Beleidskompas admin reference documents are curated shared source material, distinct from end-user uploads. They live in Postgres (table `documents`, content-addressed), and every template version keeps links to its documents, including ones removed later, so removing a document from a template does not delete the file. Generated workflow exports can contain copies of that material (preview text), and the current admin writer does not coordinate deletion from n8n's stored workflow definitions. Do not put personal/regulated user uploads in that library; assign its source and workflow copies an owner-approved retention schedule before using it for such data. Crawler history is intentionally excluded from this feature and remains bounded only by its existing item-count limit because that component is scheduled for removal.
- The n8n log-pruner treats its first run as a retention baseline; if there is an active log but no prior rotation marker, it truncates that active log rather than risk refreshing unknown-age contents.
- Docker volumes, database snapshots/backups, host filesystem snapshots, and provider-side request retention are outside this application sweep. Their retention must be configured separately; successful deletion from the running application does not erase a previously captured backup.
- External Langfuse prompts are not deleted by this application. Their owner must apply an equivalent retention policy at the source.
- The audit found a separate LiteLLM PostgreSQL database (`DATABASE_URL` is configured), as well as n8n PostgreSQL, Redis, Meilisearch, Qdrant, and pgvector. This feature does **not** disable, inspect, or purge LiteLLM request/spend records; until that database's schema and live settings are checked for prompt/completion payloads and a policy is applied there, it is not possible to claim all copies of chat data are gone after 30 days. Redis sessions/cache, search/vector indexes, provider-side logs, and backups also need their own deployment-level verification and retention controls.

## Operations

Review the values in [`.env`](../.env) against [`.env.example`](../.env.example), then recreate `govchat-retention` to apply retention-setting changes. Recreate `librechat` only when changing its independent temporary-chat behavior or other application settings. Compose validation:

```sh
docker compose --env-file .env.example config --quiet
```

After deployment, verify `govchat-retention` logs the configured retention windows and periodically inspect its logs and container status for startup or sweep failures. The worker exits non-zero on initialization failures so Compose can restart it. For retention changes, update the `.env` value and recreate `govchat-retention`; recreate other services only when their own settings changed.
